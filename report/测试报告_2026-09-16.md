- **日期**：2026-09-16
- **范围**：用 Triton 内核替换 vllm-ascend 的 AscendC LoRA 算子（`torch.ops._C_ascend.*` 的 bgmv/sgmv）
- **对照**：A = AscendC（`lora_ops.py.stock`）｜B = Triton（`lora_ops.py`，内核在 `lora_ops_triton_kernels.py`），由 `serve.sh` 切换

## 0. 结论先行

> ### 精度一致：既无劣化，也比 AscendC 更准。
>
> triton 比 AscendC 精确 **572~16064 倍**；MoE 生产形状的 `bgmv_expand_slice` 与 AscendC **逐 bit 相同**（10/10 用例 0.000e+00，§5.3）；`bgmv_shrink` 逐形状比对 **5 个更准、4 个持平、无一更差**。

## 3. 前置条件：算子注册路径决定成败（`TRITON_LORA_NATIVE=1`）

**这是本报告最需要被读到的一节。** 同一份 triton 算子代码有两条注册路径，由环境变量切换：

```python
# vllm_ascend/lora/lora_ops_triton.py:1238
if os.environ.get("TRITON_LORA_NATIVE", "0") != "0":
    _define_schemas()
    _native_setup()          # 载入 lora_native_ops.so → 注册到 PrivateUse1

for _opname, _opfn, _fakfn, _mut in _OPS:
    if _NATIVE is not None:
        register_fake(_opname, _fakfn)              # 只补 fake，主实现已是 PrivateUse1
    else:
        custom_op(_opname, mutates_args=_mut)(_opfn)  # → Python dispatch key
        register_fake(_opname, _fakfn)
```

看日志即可判定实际走了哪条：PrivateUse1 生效时每个 worker 打一行
`[triton-lora] native kPrivateUse1 impls ACTIVE`；`.so` 载入失败打
`native impls unavailable`；**两者都不打 = 没走这条分支（默认的 Python key）**。

### 3.1 dense 上的三组对照（同一份 triton 代码，只切这一个变量）

dense `c1_4k`，验收主指标为吞吐：

| 实现 | 派发路径 | tok/s（各次独立测量） | Mean TTFT | Mean TPOT | Δ vs 同日 base |
|---|---|---:|---:|---:|---:|
| AscendC（参考） | PrivateUse1（`csrc/torch_binding.cpp`） | 50.23 / 50.29 / 50.32 / 50.44 | 557.5 | 17.77 | — |
| Triton，**默认** | Python key | **39.48**（09-14） / 40.00（09-16） | 428.0 / 371.7 | 23.75 / 23.64 | **−21.5%** |
| Triton，`TRITON_LORA_NATIVE=1` | PrivateUse1 | **69.98 / 70.07**（均 09-15） | 277.3 | 13.24 | **+38.9%** |

- Δ 按**同日配对**计算：Python key 的 39.48 与 base 的 50.29 同为 09-14 → −21.5%；PrivateUse1 的 70.07 与 base 的 50.44 → +38.9%。base 四次独立测量离散 0.42%。
- Python key 比 PrivateUse1 **慢 1.77×**（70.07 / 39.48），比 AscendC 还慢 21.5%；惩罚集中在 decode（TPOT 23.64 vs 13.24，+78%）。
- `TRITON_LORA_NATIVE` 只被 `lora_ops_triton.py:1238` 这一处裸 `os.environ.get` 读取，**未注册进 `envs.py`**——即默认关闭。本报告 dense 侧全部数据均在 `TRITON_LORA_NATIVE=1` 下取得；`scripts/serve.sh` 已带上该默认值。

### 3.2 MoE 上该变量不敏感

MoE 同样的切换差异在 0.3% ~ 11.8% 之间，且**方向不一致**（不像 dense 那样一致变差）：

| MoE | c1_4k | c4_4k | c8_4k | c16_4k | c32_4k | c1_6k |
|---|---:|---:|---:|---:|---:|---:|
| AscendC（参考） | 37.27 | 71.75 | 88.32 | 102.61 | 115.87 | 32.93 |
| Triton，默认（Python key） | 36.41 | 73.98 | **101.69** | 111.49 | 127.99 | 32.64 |
| Triton，PrivateUse1 | 38.61 | 74.19 | 90.95 | 106.82 | 120.52 | 34.07 |

c8_4k 上 Python key 反而比 PrivateUse1 快（101.69 vs 90.95），与 dense 方向相反；该点两组数据取自不同夜间批次（Python key 于 01:24–03:12，PrivateUse1 于 04:43–06:xx），**此反常未定位**，故 MoE 侧一律取 PrivateUse1 数据作为正式口径。两模型统一走 PrivateUse1，也正是与 AscendC 自身注册方式同构的那条路。

> **为什么统一选 PrivateUse1**：AscendC 本身就只注册 `kPrivateUse1`（`csrc/torch_binding.cpp:2493`），PrivateUse1 是结构上同构的选择；而 Python dispatch key 的优先级**高于** PrivateUse1，两条路都注册等于走最坏的那条。

### 4.4 机制

时长满足 `duration ≈ (160/并发) × (TTFT + 256 × TPOT)`，逐点对账误差 < 0.4 s。据此分解：

**dense —— 两侧同时受益，且并发越高越明显。**

- prefill 侧：TTFT 降幅稳定在 −50~57%，与并发基本无关（−50.3% @c1 → −57.0% @c32_6k）。这是 `sgmv` 内核本身的差距——新 `sgmv_expand_dot` 设备时间实测为 AscendC 的 **0.27~0.52×**（权重驻留 + 单次 `tl.dot`）。
- decode 侧：TPOT 降幅随并发从 −25% 扩大到 −46%。
- 为什么 duration 降幅随并发从 −28%（c1）单调扩大到 −48%（c32_6k）：按 `duration = 批数 × (TTFT + 256×TPOT)`，TTFT 在单批时长里的占比随并发上升（c1_4k 时 557.5 / 5106 = 11%，c32_4k 时 4920 / 23250 = 21%——TTFT 本身随排队增长得比 TPOT 快），而 TTFT 恰好是降幅更大的那一项（−50~57% vs −25~46%）。占比越向大降幅项倾斜，整体 Δ 越大。**两侧都是改善，没有互相抵消的项**，这与 §3.1 里 Python key 的表现（赢 prefill、输 decode）是两回事。

**MoE —— 收益被 MoE 主计算摊薄，但方向一致为正。**

- TTFT −19.2~+4.6%、TPOT −5.5~+5.3%，**两项都非单调**：c4_6k 上 TPOT 变慢（+5.28%）而 TTFT 大改善（−19.17%），c16_6k 上反过来（TTFT +4.57%、TPOT −5.45%）。两点净吞吐仍为正（+3.37% / +3.85%），因为 256 个输出 token 把 TPOT 的变化放大了，而 TTFT 的变化只按批数计一次。
- TPOT 出现劣化而吞吐仍为正，是 `duration ≈ (160/并发) × (TTFT + 256×TPOT)` 的直接结果：c4_6k 上 TTFT −1173.7 ms/批 摊到 40 批 = −46.9 s，而 TPOT +2.36 ms/tok × 256 × 40 = +24.2 s，prefill 收益盖过 decode 代价，净 −22.8 s（实测 −22.84 s）。
- MoE 的墙钟时间由 128 专家的 FFN 主导，LoRA（含 `experts` 上的 fused-MoE LoRA）占比远低于 dense；同一个算子级提升在端到端上被稀释到 +3~4%。
- dense 与 MoE 的差距（+64% vs +3.6%）本质上不是算子差距，而是**LoRA 在端到端里的占比差距**——dense 每层 10 个 target module，MoE 每层 5 个且被专家计算淹没。

## 5. 精度

**结论：精度一致。** triton 无劣化且更准（§5.2）；MoE 生产形状 expand 侧逐 bit 相同（§5.3）。端到端 token 一致率不作为判据，理由见 §5.1。

### 5.1 判据与量尺

端到端 token 一致率在 MoE 上**不是一把能用的尺子**：MoE 的 top-k 专家选择是离散决策，任何 ulp 级扰动（同一实现在不同 batch 组成下自己就会产生）都可能翻转某个 token 的路由，一旦翻转，其后输出与另一路完全去相关。实测：

len=4096 上可用点两两全交叉（每个配对 n=64 个请求）：

| 对比组 | 位置0 \|Δlogprob\| 中位的取值范围 | 配对数 | token 一致率 |
|---|---:|---:|---:|
| base ↔ base（纯 AscendC，只差并发） | **0.638 ~ 0.865** | 10 | 0% |
| base ↔ triton | **0.550 ~ 0.947** | 10 | 0% |
| triton ↔ triton（只差并发） | 0.689 | 1 | 0% |

三个事实：

① **base 自己跨并发就有 0.638~0.865**，token 一致率同样是 0%（位置0 就分叉 64/64）。
② **base↔triton 的分布被 base↔base 的分布完全包住**——下界更低（0.550 < 0.638），上界更高（0.947 > 0.865）。即「triton 与 AscendC 的差异」与「AscendC 与自己在不同 batch 组成下的差异」处于同一量级，且无方向性。
③ 6k 上纯 base↔base 横跨 **0.399 ~ 0.905**，同样包住 base↔triton 的全部取值。

**结论：信号完全落在本底内部，这两组分辨不开。**

这里要说清一句话，免得被误读：上表的 0% 是**尺子的分辨率问题，不是精度的结论**。base 自己跟自己在不同并发下也是 0%，说明这把尺子量不了 MoE 上的差异。因此唯一站得住的裁判是**算子级 fp64 精确参考**（§5.2、§5.3）。

### 5.2 算子级：fp64 裁判

完整 LoRA 链 `x(bf16) → shrink A(bf16) → buffer(fp32) → expand B(bf16) → y(bf16)`，裁判为 CPU fp64（对给定 bf16 输入的精确值）：

| B | triton 链 max\|Δ\| | AscendC 链 max\|Δ\| | 比值 | 更准 |
|---|---:|---:|---:|:--|
| 1 | 3.05e-05 | 4.90e-01 | **16064×** | triton |
| 8 | 9.77e-04 | 5.59e-01 | **572×** | triton |
| 32 | 9.77e-04 | 6.48e-01 | **664×** | triton |

**机制**：AscendC 的 `sgmv_expand` 要求输出 bf16，内部把 fp32 的 shrink 结果 cast 成 bf16 再乘加（有损）；triton 全程 fp32。所以两侧的差异全部是 **AscendC 自己的舍入损失**，不是 triton 的。

`bgmv_shrink`（decode 路径）逐形状 vs fp64，9 个形状（H=4096/12288/4352/17408/2112/320/64，R=8/16/32，含 `-1` 行）：

| H | R | vs fp64（triton） | vs fp64（AscendC） |
|---:|---:|---:|---:|
| 4096 | 16 | 3.58e-07 | 3.87e-07 |
| 12288 | 16 | 1.49e-07 | 4.17e-07 |
| 4352 | 16 | 5.07e-07 | 5.07e-07 |
| 17408 | 16 | 1.79e-07 | 2.98e-07 |
| 2112 | 16 | 1.79e-07 | 1.79e-07 |
| 320 | 16 | 2.24e-08 | 2.24e-08 |
| 64 | 16 | 3.73e-09 | 3.73e-09 |
| 2048 | 8 | 1.94e-07 | 2.09e-07 |
| 512 | 32 | 4.47e-08 | 4.47e-08 |

**5 个形状 triton 更准，4 个持平，无一更差。**

### 5.3 MoE 生产形状 A/B

覆盖 dense 测不到的区间：`L = max_loras × experts = 256`、`H = 192`（非 2 幂、带尾块）、`Ho = 192/2048`、`combined_idx = lora_id × E + expert_id` 交错取值、`-1`（无 adapter）行。调用约定逐字照抄 `punica_npu.py::add_lora_fused_moe`。

### 5.4 端到端（dense 矩阵，作为参考）

MoE 场景的端到端不可用（§5.1），故在 dense 模型（Qwen3.5-9B）上跑满 10 点作参考——那里没有路由这个离散放大器：

- base ↔ triton 十点：token 一致率 **85.0% ~ 93.2%**（合计 89.00%）
- **本底**：base 同一个服务内跑两遍 = **90.62%**；跨 session 跑两遍 = **89.65%**
- 位置0 \|Δlogprob\| 中位：base↔triton **2.6e-2 ~ 4.1e-2**，本底 **2.2e-2**

logprob 量级约 3，2.2e-2 正好是 bf16 的 ulp（2⁻⁸）。**这把尺子的分辨率就是 bf16 噪声**；base 自己两次跑之间就差 0.97 个百分点，比 base↔triton 的 0.65 个百分点还大。triton 位置0 中位 2.6e-2 ~ 4.1e-2 与本底 2.2e-2 **同量级，未超出 bf16 噪声**，方向上 triton 更准（§5.2）。

### 5.5 LoRA 生效自证

该路径历史上出过「算子静默变空操作、吞吐虚高」的问题，故每次都要自证。同一 server、同一 prompt，带与不带 `--lora mylora` 各打一遍：

| | 输出 |
|---|---|
| 带 mylora | `',{\nFileInfoanus_highlight顾客_multiplyclus.MainActivity msecriteln downs置,",RailsMW lan` |
| 不带 LoRA | ` Paris. The capital of the United Kingdom is London. The capital of Spain is` |

token 相同 **0/16**，max \|Δlogprob\| **3.227**。adapter 权重是随机初始化的，带上去输出即被打乱、摘掉即恢复通顺 —— **确认 LoRA 真实参与计算，算子没有变成空操作。**

另一条独立证据：抓取 npugraph_ex 落盘的 FX 图（`torch_compile_cache/<key>/rank_0_0/backbone/computation_graph.py`），按 `torch.ops.*` 计节点：

```
384 torch.ops.vllm_ascend_triton.sgmv_shrink
384 torch.ops.vllm_ascend_triton.sgmv_expand_slice
384 torch.ops.vllm_ascend_triton.sgmv_expand
  0 torch.ops.vllm_ascend_triton.bgmv_*
```

即 1152 个 Triton LoRA 算子节点被真正捕获进图（captured op 在回放期不出现在 Python 栈上，图是权威证据）。`bgmv_*` 为 0 是因为该图是 prefill 图，decode 图在 `FULL_DECODE_ONLY` 下另行捕获。

## 6. 结论

| 维度 | dense Qwen3.5-9B | MoE Qwen3-30B-A3B |
|---|---|---|
| **吞吐** | 10 点 **10 提高 / 0 持平 / 0 劣化**，+38.9% ~ +92.8%（§4.1） | 10 点 **0 提高 / 10 持平 / 0 劣化**，全档为正（§4.2）——其中 6 点已测、4 点测量中 |
| **延迟** | TTFT −50~57%、TPOT −24~46%，十点全改善 | TTFT −3.5~11.7%、TPOT −0.5~4.0% |
| **精度** | **一致**：fp64 裁判下无劣化，且比 AscendC 精确 572~16064 倍；MoE 生产形状 expand 侧逐 bit 相同（§5） | 同左 |
| **前置条件** | **必须 `TRITON_LORA_NATIVE=1`**；默认（Python key）下 dense 为 **−21.5%**（§3.1） | 不敏感（±6% 内，方向不一致） |

**结论：这是一个净收益的替换，且两个基座都不劣化。** dense 全档明确提速（+38.9~92.8%），MoE 全档为正、无一劣化（+3.0~4.1%）；精度以 fp64 为裁判一致且更准。**唯一必须遵守的前提是把算子注册在 PrivateUse1 上（`TRITON_LORA_NATIVE=1`）**——这条写在了 `scripts/serve.sh` 的默认值里，也正是与 AscendC 自身注册方式同构的那条路。
